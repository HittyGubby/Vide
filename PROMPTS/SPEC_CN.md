# Vide — 音乐平台设计规范

> 本文档是构建 Vide 的权威设计规范。
> 面向编程代理编写，请严格遵循。

---

## 1. 愿景

面向高级用户的轻量级跨平台音乐平台。与传统音乐播放器不同，核心抽象是**一个以元数据丰富的媒体库，通过标签、过滤器和动态视图组织**——而非播放列表。

### 能力

- 本地音乐播放
- 在线音乐平台集成（通过插件）
- 视频平台集成（通过插件，如 Bilibili、YouTube）
- 跨设备同步
- 节点间远程媒体共享
- 可扩展的插件生态系统
- 低资源消耗
- 用户控制每个平台/能力的提供者路由aaa

### 技术栈

| 层级 | 技术 |
|-------|-----------|
| 核心 | Rust |
| 桌面 UI | Tauri + Svelte |
| 移动端 | 待定（Tauri Mobile 成熟时采用，否则使用 Flutter） |
| 元数据数据库 | SQLite (WAL mode) |
| 媒体缓存 | 文件系统（不使用数据库存储媒体二进制数据） |
| 插件运行时 | Node.js（随应用捆绑） |
| 进程间通信 | JSON lines over stdin/stdout |

## 2. 设计原则

### 2.1 核心拥有基础设施

核心负责以下模块：

- 存储（文件路径、缓存位置）
- 缓存（创建、淘汰、完整性）
- 流处理（网络、管道、文件读取）
- 播放管线（解码、缓冲、输出）
- 网络通信（HTTP 服务器、远程节点）
- 同步（元数据复制）
- 插件路由（能力 → 提供者映射）
- 元数据数据库（SQLite）

插件**绝不**直接：

- 写入缓存文件
- 管理下载
- 管理同步
- 响应网络请求
- 访问其他节点
- 选择文件路径

插件只提供**特定平台的逻辑**（搜索、元数据解析、流描述符生成）。

### 2.2 插件是解析器

插件回答：

- 如何在某个平台上搜索歌曲？
- 如何获取歌曲的元数据？
- 如何获取媒体流（URL + headers，或管道命令）？

插件**不**回答：

- 如何缓存？
- 如何播放？
- 如何传输字节流？
- 如何同步？
- 文件写到哪里？

**黄金法则：插件决定获取什么。核心决定如何获取。**

### 2.3 用户控制自动化

路由决策**可见且可配置**。用户可以选择每个平台上哪个提供者处理每种能力。回退顺序通过用户配置的排序列表决定。自动回退遵循用户定义的顺序。

没有隐藏的自动化。没有不透明的路由。没有推荐信息流。高级用户期望对每个决策有明确的控制——永远不假设、永远不合并、永远不隐藏。

## 3. 数据模型

### 3.1 歌曲实体

歌曲是基本的不可变对象。

```json
{
  "id": "song_id",
  "title": "歌曲名称",
  "artist": "...",
  "album": "...",
  "tags": [],
  "sources": [],
  "paths": [],
  "metadata": {}
}
```

### 3.2 歌曲标识

使用**确定性、可复现的 ID**。绝不使用随机 UUID。

对于在线来源：

```
song_id = hash(platform + source_id)
```

示例：

```
youtube:abc123   → hash("youtube:abc123")
bilibili:BVxxxx  → hash("bilibili:BVxxxx")
```

对于本地文件：

```
song_id = hash(size + mtime + first_chunk + last_chunk)
```

在扫描时懒计算，避免启动时对整个大型库进行哈希。完整内容哈希可稍后计算以确认去重。

ID 必须在不同设备间可复现（这对同步至关重要）。

### 3.3 路径（本地文件）

本地文件路径以**数组**形式存储，而非作为标识。

```json
{
  "song_id": "...",
  "paths": [
    "/Music/Russia/song.mp3",
    "/Backup/song.mp3"
  ]
}
```

**规则：**

- 路径是属性，永远不是标识
- 允许多个路径（同一文件存在于不同位置）
- 如果路径 A 消失但路径 B 存在，歌曲仍然有效
- 当文件被移动时，哈希匹配会检测到并更新路径数组
- 如果出现新路径且哈希匹配，它将被添加到现有歌曲的路径中

### 3.4 来源

一首歌曲可能在多个平台上拥有多个来源。

```json
{
  "sources": [
    { "platform": "youtube", "id": "abc" },
    { "platform": "bilibili", "id": "BVxxx" }
  ]
}
```

更换来源不会改变播放列表、标签或歌曲标识。

### 3.5 本地文件：不缓存

对于本地文件，播放直接从磁盘读取。**不复制、不缓存、不重复。**

例外：从**远程节点**获取的文件被视为在线来源，可选择性地在本地缓存。

## 4. 元数据系统

元数据独立于文件。支持用户覆盖。

### 4.1 内置属性（可搜索）

每首歌曲都有以下索引字段：

```json
{
  "title": "...",
  "artist": "...",
  "album": "...",
  "source": "...",
  "path": "...",
  "added_time": "...",
  "duration": "..."
}
```

可选的导入属性（仅存在于导入的曲目）：

```json
{
  "import_order": 3,
  "import_source": "my_playlist.m3u"
}
```

- `import_order` — 在导入列表中的位置（保留原始顺序）
- `import_source` — 该曲目从哪个文件导入

这些不是 M3U 特有的。任何未来的导入格式（cue sheets、文本文件等）都使用相同的属性。用户可以查询 `import_source:"my_playlist.m3u" sort by import_order` 来重构任何导入的列表。

`path` 是可搜索的。用户可以查询 `path contains "Russia"` 来按文件系统位置过滤。这取代了基于文件夹的组织方式，同时不引入隐藏的自动化。

### 4.2 用户覆盖

```json
{
  "file_name": "track01.mp3",
  "display_title": "自定义标题",
  "artist_override": "艺术家"
}
```

文件系统是文件**存在性**的真实来源，而非元数据展示的真实来源。

### 4.3 支持的元数据

- 标题、艺术家、专辑
- 封面图片（文件引用，非 SQLite 中的 blob）
- 歌词
- 时长
- 标签
- 用户笔记

### 4.4 封面存储

```text
covers/song_id.jpg
```

SQLite 仅存储文件路径引用。永远不要在 SQLite 中存储大型图片 blob。

## 5. 标签系统

### 5.1 设计理念

用**多维标签**取代僵化的播放列表层级。歌曲可以拥有无限数量的标签。

```text
country:russia
country:ireland
genre:pop
genre:folk
mood:dark
language:arabic
```

标签具有命名空间结构：

```
namespace:value
```

### 5.2 元标签

标签本身可以进行分类，用于 UI 组织：

```text
Country
 ├ Russia
 ├ Ireland

Genre
 ├ Pop
 ├ Folk
```

元标签仅用于 UI 展示，不用于查询。

### 5.3 不继承文件夹到标签

文件夹**仅是存储位置**，不是组织单元。标签是组织的唯一真实来源。

**被拒绝的方案：自动文件夹→标签继承。** 原因：

- 创建两个竞争的真实来源（文件夹 vs 标签）
- 当文件在文件夹间去重时会失效
- 引入隐藏的自动化（违反设计原则）
- 每个文件夹只能应用一条规则（无法从文件夹结构同时标记 `country:russia` 和 `genre:pop`）

希望基于文件夹组织的用户可以直接查询 `path contains "Russia"`。

## 6. 搜索系统

### 6.1 主搜索：结构化查询栏

主搜索栏接受**显式查询语法**，并支持标签自动补全。高级用户直接输入结构化查询：

```text
country:russia AND genre:pop AND year>2020
```

```text
(genre:pop OR genre:rock) AND NOT language:instrumental
```

```text
artist:"Miyavi" AND path contains "Japan"
```

### 6.2 查询语法

**运算符：** AND、OR、NOT，括号用于分组。

**标签过滤：** `namespace:value` — 对结构化标签进行精确匹配。

**属性过滤：** `field:value` 或 `field>value`、`field<value` — 搜索内置属性（title、artist、album、path、added_time、duration）。

**文本包含：** `path contains "Russia"` — 子串匹配。

**取反：** `NOT tag:value` 或 `!tag:value`。

### 6.2.1 解析器实现

使用 `pest` crate（PEG parser generator）进行查询解析。定义一个语法文件覆盖上述语法。这是一个成熟、广泛使用的 Rust 库——无需从头构建解析器。

### 6.3 自动补全

当用户输入时，建议：

- 标签命名空间（country、genre、mood、language...）
- 命名空间内的标签值（russia、ireland...）
- 内置属性（title、artist、album、path...）
- 最近的搜索历史

自动补全使用模糊匹配处理相似字符：`ë` 匹配 `e`，`ü` 匹配 `u` 等。使用 `unicode-normalization` crate（NFD 分解）进行重音/大小写不敏感匹配。使用 `fuzzy-matcher` crate 进行容错匹配。

### 6.4 次级搜索：模糊文本搜索

一个**可收起的**次级搜索栏，用于跨所有字段的自由文本模糊匹配。

- 默认折叠（可通过切换按钮或键盘快捷键展开）
- 跨 title、artist、album、tags、path 匹配
- 支持模糊/容错匹配（相似字符、部分匹配）
- 结果按相关性分数排序

使用场景："我不记得确切的标签，但我知道标题的一部分。"

### 6.5 排序

排序与过滤分开。支持的排序字段：

- 相关性
- 添加日期
- 播放次数
- 艺术家
- 专辑
- 时长
- 用户自定义

界面示例：

```text
搜索: "country:russia AND genre:pop"
排序: 最近添加 ▼
```

### 6.6 搜索历史

最近的搜索作为历史记录保存。用户可以一键重新执行任何先前的查询。

历史记录按最近使用排序。没有单独的"保存查询"概念——直接复用历史记录。

## 7. 播放列表系统

### 7.1 库视图

主要界面是一个由当前查询驱动的**单一库视图**。v1 中没有多个命名播放列表的概念。用户输入查询，查看匹配的歌曲，播放它们。

搜索历史保存之前的查询。用户可以一键回顾任何过去的查询。

对于需要显式排序的集合，用户可以创建静态播放列表（有序引用列表）。但主要工作流是查询驱动的。

### 7.2 导入

**M3U 与 M3U8 的区别：** 不要依赖文件扩展名。进行文件内容嗅探：如果包含 `#EXT-X-` 指令，则是 HLS 清单（M3U8）——直接交给 mpv 处理，不要解析。否则，将其视为简单的 M3U 播放列表目录。

**M3U 导入（核心功能，非插件）：**

1. 解析 M3U 文件（使用成熟的 Rust M3U 解析 crate）
2. 对于每个条目：
   - 将相对路径解析为绝对路径（基准 = M3U 文件所在目录）
   - 外部 URL（http/https）按原样导入（在线来源条目，无本地路径）
   - 提取 `#EXTINF` 元数据（标题、时长）以预填充歌曲信息
3. 通过路径匹配或元数据匹配将条目映射到内部歌曲 ID
4. 如果未找到匹配 → 创建"未解析条目"（占位符）
5. 为每个导入的曲目设置 `import_order`（在列表中的位置）和 `import_source`（M3U 文件名）
6. 导入的播放列表是静态有序列表（通过 `import_order` 保留顺序）

**Spotify 导入：** 不支持（受 DRM 保护，yt-dlp 无法处理）。留给未来的插件。

## 8. 存储架构

### 8.1 SQLite（仅存储元数据）

存储：

- 歌曲元数据、标签、属性
- 播放列表和保存的查询
- 用户设置
- 插件配置和路由表

**不**存储媒体文件或大型二进制数据。

### 8.2 媒体缓存（文件系统）

```text
cache/
  abc123.media
  def456.media
  index.json
```

`index.json`：

```json
{
  "abc123": {
    "path": "cache/abc123.media",
    "size": 123456,
    "source": "youtube",
    "ttl": 999999
  }
}
```

**为什么不用 SQLite 存储媒体？** 写放大、fsync 开销、不必要的磁盘搅动。对于媒体应用，文件优先是正确的选择。

### 8.3 缓存策略

**默认：永久保留缓存。**

仅在以下情况淘汰：

1. 用户显式刷新（使条目失效）
2. 文件变为无效（缺失、哈希不匹配）
3. 超过磁盘限制（例如 20GB 上限）

支持：

- 固定媒体（永不淘汰）
- 按歌曲手动刷新
- 全局缓存大小限制

### 8.4 淘汰详情

每个条目的缓存记录：

```json
{
  "id": "abc",
  "path": "...",
  "size": 123,
  "last_used": 123456,
  "source": "youtube",
  "valid": true
}
```

淘汰顺序：

1. 磁盘压力：总缓存 > 限制
2. 损坏：文件缺失或哈希不匹配
3. 可选的 LRU 回退：最近最少使用 + 未固定

## 9. 插件系统

### 9.1 架构

插件是**外部进程**，通过 JSON lines over stdin/stdout 进行通信。没有 ABI、没有 WASM、没有嵌入式运行时。

```
Core (Rust)  ←→  stdin/stdout JSON  ←→  插件进程 (Node.js)
```

### 9.2 插件运行时

- **语言：** 任意。插件可以使用任何能够读取 stdin 和写入 stdout 的语言编写。
- **不捆绑运行时。** 核心不附带 Node.js、Python 或任何特定运行时。预期高级用户会安装他们偏好的运行时。
- **执行方式：** 核心启动插件清单中指定的进程。清单声明完整的 exec 命令。
- **无依赖管理。** 插件作者自行捆绑依赖。核心不管理安装。
- **插件目录：** 设置中的单个可配置路径（默认：`~/.config/vide/plugins/` 或平台等效路径）。需要多个来源的用户可以使用符号链接。

**被拒绝的 LX Music 侧载方式。** LX Music 在 Electron 中嵌入 JS，使用自定义 `lx.fetch` 绕过 CSP/CORS。这是浏览器上下文的 hack。子进程模型严格更优：完整的系统访问、无沙箱限制、无自定义 API 包装器、支持任何语言。

### 9.3 插件清单

每个插件有一个清单，声明如何运行以及提供什么：

```json
{
  "name": "yt-dlp",
  "version": "1.0",
  "exec": ["node", "yt-dlp-plugin.js"],
  "methods": ["resolve", "stream_info"],
  "capabilities": [
    { "type": "search", "platform": "youtube" },
    { "type": "resolve", "platform": "youtube" },
    { "type": "stream", "platform": "youtube" }
  ]
}
```

`exec` 是一个数组：要启动的命令和参数。示例：

- `["node", "plugin.js"]` — Node.js 插件
- `["python3", "plugin.py"]` — Python 插件
- `["./plugin-binary"]` — 编译的二进制文件
- `["bash", "plugin.sh"]` — shell 脚本

核心启动清单中声明的任何内容。它不关心语言。

### 9.4 基于能力的注册

启动时，每个插件注册其能力。核心构建路由表：

```text
youtube/search   → yt-dlp, youtube-native
youtube/stream   → yt-dlp
youtube/metadata → youtube-native
bilibili/search  → yt-dlp
bilibili/stream  → yt-dlp
```

核心查询其路由表——没有运行时猜测。

### 9.5 能力类型

初始集合（可扩展）：

- `search`
- `metadata`
- `playback`（流解析）
- `lyrics`
- `recommendation`

系统必须允许未来的能力类型而无需重新设计。

### 9.6 路由与编排

**按平台、按能力的提供者选择。** 不是全局的插件启用/禁用。

路由 UI 如下：

```text
平台: Bilibili
──────────────────
搜索     [Native ▼]
播放     [yt-dlp ▼]
元数据   [Native ▼]
歌词     [Native ▼]

回退顺序:
1. Native
2. yt-dlp
3. Mirror Plugin

☑ 自动回退
```

- 每个能力每个平台一个下拉菜单（可拖拽重新排序）
- "自动回退"开关遵循下拉菜单顺序
- 运行时状态指示器显示活跃的提供者：`Playing via: yt-dlp`
- "默认提供者"选项用于继承（避免逐个配置 20 个平台）

**路由表持久化在 SQLite 中。** 启动时，核心从插件目录加载清单，与保存的路由配置合并，并构建运行时路由表。

### 9.7 所有能力都是排他的

**每个能力都是排他的。** 每个平台每个能力一个提供者。不合并、不并行查询、不结果去重。

理由：高级用户想要明确的控制。合并多个提供者的结果会引入不可预测的行为、重复条目和不一致的元数据。选择一个提供者，获取一个结果集。

| 能力 | 行为 |
|-----------|----------|
| 搜索 | **排他** — 每个平台一个提供者 |
| 元数据 | **排他** — 每个平台一个权威来源 |
| 播放/流 | **排他** — 一个提供者处理下载 |
| 歌词 | **排他** — 一个来源 |

回退顺序仅在主要提供者失败（错误、超时、不可用）时使用。

### 9.9 歌曲标识解耦

搜索结果通过 **platform + source_id** 标识项目，绝不通过插件名称：

```json
{
  "platform": "youtube",
  "id": "abc123"
}
```

而不是：

```json
{
  "plugin": "yt-dlp",
  "id": "abc123"
}
```

这确保插件替换不会破坏播放列表或引用。

## 10. 插件接口

### 10.1 消息协议

所有通信使用 **JSON lines over stdin/stdout**。没有 gRPC，没有自定义序列化。

**请求（核心 → 插件）：**

```json
{"id": "t123", "action": "search", "params": {"q": "歌曲名称", "platform": "youtube"}}
```

**响应（插件 → 核心）：**

```json
{"id": "t123", "result": [...]}
```

**错误：**

```json
{"id": "t123", "error": "not_supported"}
```

### 10.2 插件操作

每个插件声明其支持的操作：

- `search` — 在平台上搜索歌曲
- `resolve` — 解析已知歌曲的元数据
- `stream` — 返回用于播放的流描述符

### 10.3 流描述符

插件返回**描述符**，绝不执行下载。只有两种有效的输出类型：

**类型 A — 直接 URL 流：**

```json
{
  "id": "t123",
  "type": "url_stream",
  "url": "https://cdn.example.com/media.mp3",
  "headers": {
    "Referer": "https://example.com",
    "User-Agent": "..."
  }
}
```

**类型 B — 子进程管道（如 yt-dlp）：**

```json
{
  "id": "t123",
  "type": "stream",
  "exec": {
    "cmd": ["yt-dlp", "-o", "-", "https://..."],
    "mode": "stdout"
  }
}
```

核心执行描述符：对于 `url_stream`，通过 HTTP 获取；对于 `stream`，启动进程并读取 stdout。

### 10.4 规则

- 插件绝不选择文件路径
- 插件绝不写入磁盘
- 插件绝不管理缓存
- 插件仅返回结构化数据
- 插件使用 **stdout** 进行 JSON 通信，**stderr** 用于日志/调试输出
- 核心完全忽略 stderr
- 核心忽略任何不是有效 JSON 的 stdout 行
- 如果插件用非 JSON 输出污染 stdout，那是插件作者的 bug

### 10.5 错误处理

- 插件以非零状态退出 → 视为失败，核心触发回退
- 插件挂起 → 核心强制执行每个操作的超时（搜索：10 秒，流：30 秒，解析：5 秒），然后终止进程
- 插件在请求中途崩溃 → 核心取消任务，触发回退
- 回退逻辑完全在核心侧：重试下一个提供者、跳到下一个项目等

## 11. 进程管理

### 11.1 任务表

核心为每个进行中的操作维护一个任务表：

```text
task_table[t123] = {
  plugin: yt-dlp,
  process: PID,
  status: running
}
```

支持：进度报告、取消、超时、重试。

### 11.2 取消

取消是**基于进程的**，不是基于消息的。

当用户跳过歌曲时：

1. 将任务标记为已取消
2. 向子进程发送 SIGTERM
3. 超时后降级为 SIGKILL
4. 丢弃待处理的输出
5. 立即通知 UI

防止后台任务堆积。

### 11.3 并发限制

**每个插件的并发限制**防止请求风暴（LX Music 冻结问题）：

```json
{
  "yt-dlp": { "max_concurrent": 2 }
}
```

核心强制排队。这本身就防止了"15 个 HTTP 请求导致冻结"的场景。

## 12. yt-dlp 集成

### 12.1 角色

yt-dlp 被视为提供者插件（或内置核心能力）。它处理所有下载复杂性：DASH/HLS、格式选择、片段合并、签名刷新。

### 12.2 格式支持

应用应支持**尽可能多的媒体格式**（mp3、flac、ogg、opus、aac、m4a、wav、mp4、mkv、webm 等）。对于视频文件，**直接播放音频轨道**，无需提取。没有 FFmpeg 依赖。播放器只需打开文件并读取音频流——视频轨道被播放管线忽略。

### 12.3 首选模式：子进程管道

```bash
yt-dlp -o - URL
```

媒体通过 stdout 流传输。核心：

1. 启动 yt-dlp 进程
2. 将 stdout 作为字节流读取
3. 写入缓存文件和/或直接提供给播放器
4. 不需要中间文件

### 12.4 元数据模式

仅用于元数据解析：

```bash
yt-dlp -j URL
```

返回包含 `url`、`http_headers`、`formats[]` 等的结构化 JSON。核心可以使用这些 headers 直接获取。

### 12.5 分层策略

**第一层（首选）：** 插件返回 URL + headers → 核心直接获取。

**第二层（针对困难平台的回退）：** 插件返回管道命令 → 核心启动进程并读取 stdout。

**绝不：** 插件下载文件 → 写入磁盘 → 核心读取。（这是 LX 风格的失败模式。）

## 13. 网络

> **重要：** 本系统中所有媒体传输使用 **HTTP octet-stream**（字节的分块传输），就像提供静态文件一样。这不是实时流媒体。不要实现 RTSP、RTMP 或任何流媒体协议。HLS/DASH 的复杂性由 yt-dlp/mpv 处理，而不是核心 HTTP 服务器。核心服务器只需打开文件（或管道）并将字节写入 HTTP 响应。

### 13.1 远程共享是核心功能

远程共享是**核心功能**，不是插件。它需要访问标识、存储和网络层——这些都是核心拥有的。

### 13.2 HTTP API

```http
GET /song/{id}          → 媒体流 (octet-stream)
GET /meta/{id}          → JSON 元数据
GET /cover/{id}         → 封面图片
GET /search?q=...       → 通过插件系统搜索
GET /status             → 当前播放状态（一次性）
GET /status/stream      → 播放状态变更的 SSE 流
GET /now-playing        → 流式传输当前曲目的音频（动态）
```

`{id}` 是歌曲 ID（确定性哈希，例如 `a1b2c3d4e5f6...`）。

### 13.3 播放器状态（SSE）

通过 Server-Sent Events 实现实时播放状态。

`GET /status/stream` 在状态变更时推送事件：

```json
{"type":"track_change","data":{"id":"...","title":"...","artist":"...","duration":300}}
{"type":"state_change","data":{"state":"playing"}}
{"type":"progress","data":{"position":45.2,"duration":300}}
{"type":"track_switching"}
```

`track_switching` 事件告诉客户端曲目即将切换，以便他们准备重新连接或重新获取。

`GET /status` 以一次性 JSON 响应返回当前状态（用于初始加载或轮询回退）。

`GET /now-playing` 动态流式传输当前曲目的音频。当曲目切换时，服务器发送 `track_switching` SSE 事件，客户端重新连接到新曲目。

### 13.4 访问模式

服务器返回可用的访问模式。**没有优先级字段**——客户端决定顺序。

```json
{
  "id": "a1b2c3d4e5f6...",
  "sources": [
    { "type": "url", "url": "https://cdn..." },
    { "type": "stream", "endpoint": "/song/a1b2c3d4e5f6..." }
  ]
}
```

**服务器是权威的** — 决定哪些模式可用。客户端按其首选顺序尝试模式（通常是 URL 优先，然后流回退）。

**URL 模式：** 低服务器负载，直接 CDN 访问。

**流模式：** 服务器从本地缓存流式传输字节。用于本地文件、私有内容、需要认证的内容、跨设备共享。

### 13.5 远程歌曲标识

远程内容以普通来源的形式出现：

```json
{
  "platform": "remote",
  "node": "deviceA",
  "id": "a1b2c3d4e5f6..."
}
```

`id` 是歌曲 ID（确定性哈希）。远程节点直接使用此 ID — 无需额外哈希。

核心透明地处理传输。插件不参与远程流传输。

## 14. 分布式节点

### 14.1 节点角色

每个实例可以充当：

- 客户端（从其他节点消费）
- 服务器（共享其库）
- 混合模式（两者兼有）

### 14.2 共享内容

- 元数据、标签、播放列表、设置（始终共享）
- 缓存的媒体（可选）
- 不共享插件状态

### 14.3 远程来源

当节点 B 从节点 A 请求时：

```http
GET /song/abc123
```

节点 A 打开本地缓存文件并流式传输字节。不涉及插件。

### 14.4 同步

同步是**核心管理**的复制：

- 推送差异，而非完整状态转储
- 复制：元数据、标签、播放列表、设置
- 媒体复制是可选的
- 插件从不参与同步

## 15. UI 与应用架构

### 15.1 UI ↔ 核心通信

Tauri UI 通过 **Tauri commands**（内置 IPC 机制）与 Rust 核心通信。JS 前端调用 `invoke("command_name", {args})`，Rust 后端处理。本地 UI 通信不使用 HTTP、WebSocket。

### 15.2 配置

所有用户配置存储在 **SQLite 设置表**中（与元数据相同的数据库）。没有单独的配置文件。单一真实来源。

### 15.3 日志

核心使用 `tracing` crate（Rust）进行结构化日志记录。插件使用 stderr 输出自己的日志。核心忽略插件的 stderr。

### 15.4 UI 原则

- **可发现性**优于隐藏的自动化
- **可见性**优于不透明的路由
- **高级用户控制**优于默认设置

### 15.5 提供者状态

在播放时显示活跃的提供者：

```text
Playing via: yt-dlp
Metadata via: Native
Lyrics via: Native
```

可点击的状态徽章用于快速切换。

### 15.6 没有推荐

没有歌曲推荐。没有"发现"信息流。没有干扰。用户控制一切。

## 16. 库管理

### 16.1 库根目录

用户定义要扫描的根目录：

```json
{
  "library_roots": [
    "/Music",
    "/Downloads/Music"
  ]
}
```

核心递归扫描这些目录中的所有支持的媒体格式（音频和视频 — 视频文件会提取音频轨道）。

### 16.2 文件扫描

在扫描期间，对于每个文件：

1. 计算快速哈希：`hash(size + mtime + first_chunk + last_chunk)`
2. 检查哈希是否匹配现有歌曲 → 更新路径数组
3. 如果不匹配 → 创建新的歌曲实体
4. 完整内容哈希稍后懒计算以确认去重

### 16.3 去重

当同一文件存在于多个位置时：

- 在扫描期间检测到哈希匹配
- 路径数组更新：`["/Music/Russia/song.mp3", "/Backup/song.mp3"]`
- 歌曲实体保持单一，存储位置是复数
- 免费的完整性功能：如果路径 A 消失，路径 B 保持歌曲有效

### 16.4 本地文件的播放回退

```text
1. 本地路径（路径数组中第一个可用的）
2. 本地重复路径（其他路径）
3. 远程缓存（来自已连接的节点）
4. 远程流（来自已连接的节点）
```

用户可配置的顺序。

### 16.5 文件夹处理

文件夹是**存储根目录和发现来源**，不是组织单元。

- 用户设置库根路径
- 核心递归扫描所有支持的格式
- 文件系统路径是可搜索的属性（`path contains "Russia"`）
- 不自动继承文件夹到标签
- 没有文件夹即播放列表的概念
- 用户通过标签而非文件夹组织

## 17. 构建顺序（原型）

对于第一个原型，**推迟**：

1. 跨设备同步
2. 插件市场
3. 远程共享
4. 移动端支持

**首先构建：**

1. 具有异步运行时的 Rust 核心（Tokio）
2. SQLite 元数据层（WAL mode）
3. 标签系统（多维，带有元标签）
4. 本地媒体支持（库根目录、扫描、音频+视频格式支持）
5. 带索引的文件系统缓存
6. 插件系统（进程生成、JSON IPC、清单加载）
7. yt-dlp 提供者插件（流管道模式）
8. 提供者路由 UI（按平台能力选择、可拖拽回退）
9. 搜索系统（带有自动补全的结构化查询栏 + 模糊文本搜索）

仅这些就已经在架构上超越 LX Music，并在日常使用中验证了该模型。
